# RESEARCH REPORT: RENZO PHASE 2 ANALYSIS

## EXISTING_FEATURES

### Authentication & User Management
- `login()` - Hardcoded demo login (demo/password)
- `logout()` - Clears localStorage and returns to login
- `getCurrentUser()` - Returns stored user from localStorage
- User session stored in `localStorage.currentUser`

### Contact Management (CRUD)
- `loadContacts()` - Loads from localStorage.contacts
- `saveContact(contact)` - Creates/updates contacts with ID generation
- `deleteContact(id)` - Removes contact by ID
- Contact fields: id, name, email, company, tier (A/B/C), frequency (days), lastContact (date), notes
- Contact list view with sorting and filtering
- Modal-based contact form (add/edit)

### AI Message Generation
- `generateMessage(contact)` - Uses OpenRouter API with Claude Sonnet 3.5
- Considers: contact name, company, tier, frequency, days since last contact, user's company name/voice/products
- Shows loading spinner during generation
- Error handling for API failures
- Message displayed in modal with copy-to-clipboard option

### Queue/Drafts System
- "Queue" view shows contacts needing outreach
- Queue logic: filters contacts where daysSince >= frequency OR lastContact is null
- Queue items show: contact name, company, days overdue, tier badge
- Actions: "Generate Message" and "Mark as Sent"
- `markAsSent(contactId)` - Updates lastContact to current date

### Settings Management
- Settings stored in `localStorage.userSettings`
- Fields: companyName, businessDescription, products, communicationStyle, openRouterApiKey
- Onboarding modal (first-time setup)
- Settings page with form to update all fields

### Dashboard/Statistics
- Shows total contacts count
- Shows active relationships (contacts contacted within frequency window)
- Shows overdue contacts count
- Displays greeting with current date
- Recent activity list (recent contacts by lastContact date)

### UI/Navigation
- Sidebar navigation: Dashboard, Contacts, Queue, Settings
- Active nav highlighting
- Responsive layout (sidebar + main content)
- Modal system for forms and messages
- Toast/alert system (not implemented, uses alerts)

### Data Persistence
- All data in localStorage
- Keys: `currentUser`, `contacts`, `userSettings`
- No backend/database

### Styling
- Custom CSS with Inter font
- Color scheme: #2D6A4F (green), #F7F4EF (beige), #1A1A1A (dark)
- Responsive grid layouts
- Badge system for tiers (A/B/C)
- Status pills (overdue/due/ok)

## RISKS

### Data Migration
- **RISK**: Existing contacts in localStorage lack new fields (contractExpiry, invoiceAmount, etc.)
- **MITIGATION**: Add default values on load, or migration script to add null/0 defaults

### Priority Score Complexity
- **RISK**: Users may not understand how priority score is calculated
- **MITIGATION**: Add tooltip/help text, show score breakdown on hover

### Gmail Integration Limitations
- **RISK**: mailto: links have length limits (~2000 chars), may truncate long messages
- **RISK**: gmail.com URL scheme may not work on all browsers/devices
- **MITIGATION**: Detect message length, warn user, offer copy-to-clipboard fallback

### Weight Configuration UX
- **RISK**: Users may set weights that don't sum to 100%, causing confusion
- **MITIGATION**: Auto-normalize weights or provide real-time validation feedback

### Trigger Detection Edge Cases
- **RISK**: Multiple triggers for one contact (expiry soon AND invoice overdue) - which to prioritize?
- **MITIGATION**: Define trigger priority hierarchy (e.g., invoice > expiry > recency)

### API Cost
- **RISK**: Batch message generation could consume many API tokens quickly
- **MITIGATION**: Add confirmation dialog showing estimated token cost, rate limiting

### Date Handling
- **RISK**: Contract expiry dates in past, invoice amounts negative, relationship scores out of range
- **MITIGATION**: Input validation, date picker constraints

### Performance
- **RISK**: Priority score calculation on every queue load may be slow with many contacts
- **MITIGATION**: Cache scores with timestamp, recalculate only when contact data changes

### Backwards Compatibility
- **RISK**: Removing tier A/B/C system entirely may confuse existing users
- **MITIGATION**: Keep tier as optional visual indicator, but don't use for queue logic
