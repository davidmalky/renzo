# TECHNICAL SPECIFICATION: SYNC EXECUTION ENGINE AND STATUS DASHBOARD

## OVERVIEW

This system implements a comprehensive bidirectional synchronization engine between Salesforce and Renzo with real-time monitoring capabilities. The engine executes field mappings through a background job processor with batch processing, conflict resolution, field transformation, and intelligent retry logic. A real-time status dashboard provides complete visibility into sync operations with progress tracking, error reporting, audit trails, and manual control capabilities.

## VIEWS

### SyncDashboard
Main monitoring interface showing sync operations overview. Contains four primary sections: (1) Active Sync Monitor displaying currently running syncs with live progress bars, contact counts, elapsed time, and cancel buttons; (2) Statistics Cards showing key metrics including total contacts synced today, 24-hour success rate percentage, average sync duration, and pending retry count; (3) Quick Actions Panel with "New Sync" button, "Pause All" button, date range selector, and filter criteria dropdown; (4) Sync History Table showing recent sync jobs with columns for sync ID, start time, duration, direction, status badge, contacts processed/succeeded/failed counts, and action buttons (view details, retry, download logs).

### SyncDetailsModal
Detailed view for individual sync operation. Header shows sync ID, status badge, timestamp range, and direction indicator. Content divided into tabs: (1) Overview Tab displaying summary statistics cards, progress visualization, performance metrics (contacts per second), and elapsed time tracker; (2) Logs Tab with real-time log stream showing timestamp, level, message, and expandable stack traces; (3) Errors Tab presenting failed contacts table with contact ID, field name, error message, retry count, and "Retry Single" button; (4) Changes Tab listing all successful field updates with before/after values in a diff-style format.

### NewSyncModal
Configuration interface for initiating manual sync. Contains: (1) Sync Direction selector with three radio options (Salesforce to Renzo, Renzo to Salesforce, Bidirectional); (2) Scope Configuration with radio options for "All Contacts" or "Filtered"; (3) Filter Criteria section (shown when filtered selected) with date range inputs (updated after, created after), contact source dropdown, and tag selector; (4) Advanced Options collapsible section containing batch size input (default 200), priority level selector, conflict resolution strategy override dropdown, and "Dry Run" checkbox; (5) Preview panel showing estimated contact count and affected fields list.

### ContactSyncHistoryModal
Audit trail for individual contact synchronization history. Header displays contact name, Salesforce ID, Renzo ID, and total sync count. Main content shows timeline of sync events with: (1) Event cards showing timestamp, sync ID reference, sync direction badge, and status; (2) Field Changes section per event listing field name, old value, new value, transformation applied, and conflict resolution used; (3) Error History section showing any failures with error message, retry attempts, and resolution timestamp; (4) Export button to download complete history as CSV.

### SyncConfigurationPanel
Scheduling and automation settings accessible from dashboard. Contains: (1) Schedule Configuration with options for manual only, interval-based (with cron expression builder), or webhook-triggered; (2) Default Settings including default batch size, default conflict resolution strategy, retry attempt limits, and exponential backoff parameters; (3) Rate Limiting section with Salesforce API limit display, throttle delay input, and circuit breaker threshold; (4) Notification Settings with webhook URLs for sync completion/failure, email alerts toggle, and Slack integration input; (5) Pause/Resume Controls with "Pause All Syncs" button, resume schedule selector, and emergency stop button.

## FUNCTIONS

### initializeSyncEngine()
Startup function that initializes the sync engine subsystem. Step 1: Load configuration from environment variables and database (batch size, retry limits, API credentials). Step 2: Establish database connection pool with proper timeouts and connection limits. Step 3: Initialize Redis connection for job queue and distributed locking. Step 4: Validate Salesforce and Renzo API connectivity by making test calls. Step 5: Load active mappings from mapping_configurations table where enabled=true. Step 6: Start background worker threads/processes based on concurrency setting. Step 7: Initialize rate limiter with Salesforce API limits (default 15000/day). Step 8: Set up event emitter for real-time dashboard updates via WebSocket. Step 9: Resume any paused syncs from previous session by checking sync_logs for status='paused'. Step 10: Schedule cron jobs based on interval configurations. Step 11: Register signal handlers for graceful shutdown. Step 12: Emit 'engine:ready' event.

### startSync(syncConfig)
Initiates a new synchronization operation. Parameters: syncConfig object containing direction (sf_to_renzo/renzo_to_sf/bidirectional), filterCriteria (dateRange, source, tags), batchSize, priority, conflictStrategy override, dryRun boolean. Step 1: Validate syncConfig parameters and check required fields. Step 2: Generate unique sync_id using UUID. Step 3: Insert initial record into sync_logs table with status='pending', direction, started_at=now(). Step 4: Acquire distributed lock using Redis to prevent concurrent syncs on same contact set. Step 5: Fetch contact IDs matching filter criteria from appropriate system (query Salesforce for sf_to_renzo, query Renzo for renzo_to_sf). Step 6: Divide contact IDs into batches based on batchSize parameter. Step 7: Create job entries in sync_jobs queue table with sync_id, batch_number, contact_ids array, status='queued'. Step 8: Update sync_logs with estimated_contacts count. Step 9: Emit 'sync:started' event with sync_id and metadata. Step 10: If priority is high, push jobs to priority queue, else standard queue. Step 11: Return sync_id and estimated details to caller. Step 12: If dryRun is true, execute validation only and return preview without actual data modification.

### processSyncJob(jobId)
Worker function that processes a single batch job from the queue. Parameters: jobId from sync_jobs table. Step 1: Retrieve job details from sync_jobs table including sync_id, batch_number, contact_ids, retry_count. Step 2: Update job status to 'processing' with processing_started_at timestamp. Step 3: Retrieve sync configuration and mapping rules from mapping_configurations for this sync_id's direction. Step 4: For each contact_id in batch: call syncSingleContact(). Step 5: Collect results into succeeded array and failed array with error details. Step 6: Update sync_jobs record with contacts_succeeded count, contacts_failed count, status='completed' or 'failed'. Step 7: Insert detailed records into sync_contact_results table with contact_id, sync_id, status, error_message, field_changes_json. Step 8: Update parent sync_logs record by incrementing contacts_processed, contacts_succeeded, contacts_failed. Step 9: Emit 'batch:completed' event with progress percentage. Step 10: If any contacts failed and retry_count < MAX_RETRIES, schedule retry job with exponential backoff delay (2^retry_count * BASE_DELAY). Step 11: Release rate limiter tokens. Step 12: If this was the last batch, call finalizeSyncOperation(sync_id).

### syncSingleContact(contactId, syncDirection, mappingRules)
Synchronizes a single contact between systems. Parameters: contactId (string), syncDirection (enum), mappingRules (array of mapping objects). Step 1: Fetch contact data from source system using appropriate API (getSalesforceContact or getRenzoContact). Step 2: Fetch contact data from destination system to check for conflicts. Step 3: Initialize changeSet object to track modifications. Step 4: For each mapping rule in mappingRules: call determineFieldValue(). Step 5: For each field in changeSet: call applyTransformation() based on transformation_type. Step 6: Compare source and destination values to detect conflicts. Step 7: For each conflict: call resolveConflict() with conflict_resolution_strategy. Step 8: Build update payload with resolved values. Step 9: Validate payload against destination system schema. Step 10: Execute API call to update destination contact (updateSalesforceContact or updateRenzoContact). Step 11: Insert audit record into contact_sync_history table with before/after values. Step 12: Return success with changes array or throw error with details for catch handler.

### determineFieldValue(sourceData, destData, mappingRule)
Determines the value for a single field based on mapping rule. Parameters: sourceData (object), destData (object), mappingRule (object with source_field, dest_field, direction, conflict_resolution). Step 1: Extract source value using mapping_rule.source_field path (supports nested fields with dot notation). Step 2: Extract destination value using mapping_rule.dest_field path. Step 3: Check if values differ (deep equality check for objects). Step 4: If no difference, return null (no sync needed). Step 5: Check if mapping rule has update_condition expression. Step 6: If condition exists, evaluate updateCondition() and return null if false. Step 7: Check last_modified timestamps on both source and dest objects. Step 8: Return object containing {field: dest_field, sourceValue, destValue, lastModifiedSource, lastModifiedDest, requiresConflictResolution: boolean}. Step 9: Handle null/undefined values according to mapping_rule.null_handling strategy. Step 10: Apply any default values specified in mapping rule.

### resolveConflict(conflictData, strategy)
Implements conflict resolution logic for competing field values. Parameters: conflictData (object with sourceValue, destValue, lastModifiedSource, lastModifiedDest), strategy (enum: newest_wins, salesforce_wins, renzo_wins, manual_review). Step 1: If strategy is 'newest_wins', compare lastModifiedSource with lastModifiedDest timestamps. Step 2: Return value from most recently modified system. Step 3: If strategy is 'salesforce_wins', always return sourceValue when direction is sf_to_renzo, else destValue. Step 4: If strategy is 'renzo_wins', always return sourceValue when direction is renzo_to_sf, else destValue. Step 5: If strategy is 'manual_review', insert record into conflict_review_queue table with contact_id, field_name, source_value, dest_value, sync_id. Step 6: Update sync job to status='requires_review' and pause processing. Step 7: Emit 'conflict:manual_review_required' event for dashboard notification. Step 8: Return null to skip field update pending manual resolution. Step 9: Log conflict resolution decision to sync_logs_details. Step 10: Handle custom strategy if user-defined resolution function exists.

### applyTransformation(value, transformationType, transformConfig)
Applies configured transformation to a field value. Parameters: value (any type), transformationType (enum), transformConfig (optional params object). Step 1: If value is null/undefined and transformConfig.skipNull is true, return value unchanged. Step 2: Switch on transformationType: 'trim' calls value.trim(). Step 3: 'uppercase' calls value.toUpperCase(). Step 4: 'lowercase' calls value.toLowerCase(). Step 5: 'format_phone' calls formatPhoneNumber(value, transformConfig.region). Step 6: 'format_date' calls formatDate(value, transformConfig.formatString). Step 7: 'concatenate' combines multiple fields using transformConfig.fields and transformConfig.separator. Step 8: 'substring' extracts using transformConfig.start and transformConfig.length. Step 9: 'replace' performs regex or string replacement with transformConfig.pattern and transformConfig.replacement. Step 10: 'custom' executes user-defined JavaScript function from transformConfig.functionBody in sandboxed context. Step 11: Validate transformed value type matches destination field schema. Step 12: Return transformed value or throw TransformationError with details.

### handleAPIError(error, context)
Centralized error handling for API failures. Parameters: error (Error object), context (object with sync_id, contact_id, operation, attempt_number). Step 1: Extract error type from error object (network, authentication, rate_limit, validation, server_error). Step 2: Log error to sync_logs_errors table with full stack trace and context. Step 3: If error is rate_limit (429 status), activate circuit breaker and sleep until reset time. Step 4: If error is authentication (401), attempt token refresh using refreshAuthToken(). Step 5: If refresh succeeds, return {shouldRetry: true, delay: 0}. Step 6: If error is network timeout or 5xx server error, calculate exponential backoff delay. Step 7: Check if attempt_number < MAX_RETRIES (default 5). Step 8: If retries remaining, return {shouldRetry: true, delay: Math.min(2^attempt_number * 1000, 300000)}. Step 9: If max retries exceeded, mark contact as failed and store in failed_contacts table. Step 10: Update metrics counter for error type. Step 11: If error rate exceeds threshold (>10% failures), emit 'sync:critical_error' alert. Step 12: Return {shouldRetry: false, finalError: error} for permanent failures.

### finalizeSyncOperation(syncId)
Completes sync operation and updates final statistics. Parameters: syncId (string UUID). Step 1: Retrieve all batch job results for this sync_id from sync_jobs table. Step 2: Calculate total contacts_processed, contacts_succeeded, contacts_failed. Step 3: Calculate sync duration by comparing started_at with current time. Step 4: Update sync_logs record with status='completed', completed_at=now(), final counts. Step 5: If any contacts failed, aggregate errors_json from all batches into summary. Step 6: Calculate success_rate percentage. Step 7: Store performance metrics (avg time per contact, api_calls_made, data_transferred_bytes). Step 8: Release distributed lock for this sync_id. Step 9: Clean up processed jobs from sync_jobs queue table. Step 10: Emit 'sync:completed' event with full results for dashboard update. Step 11: If notification webhooks configured, call sendSyncNotification(). Step 12: Archive old sync_contact_results records if retention policy requires.

### pauseSync(syncId)
Pauses an active sync operation. Parameters: syncId (string UUID). Step 1: Validate that sync exists and is currently in 'processing' status. Step 2: Set atomic pause flag in Redis using key "sync:{syncId}:pause". Step 3: Update sync_logs status to 'paused' with paused_at timestamp. Step 4: Send pause signal to all worker processes handling this sync_id. Step 5: Wait for active batch jobs to complete current contact (up to 30 second timeout). Step 6: Update in-progress sync_jobs to status='paused'. Step 7: Store pause context including last processed contact_id for resume. Step 8: Emit 'sync:paused' event with sync_id and progress snapshot. Step 9: Log pause action to audit log with user_id if manually triggered. Step 10: Return current progress statistics and estimated remaining work.

### resumeSync(syncId)
Resumes a paused sync operation. Parameters: syncId (string UUID). Step 1: Validate sync exists and status is 'paused'. Step 2: Clear pause flag from Redis. Step 3: Retrieve pause context including last processed contact. Step 4: Query sync_jobs for jobs with status='paused' for this sync_id. Step 5: Update sync_logs status back to 'processing' with resumed_at timestamp. Step 6: Requeue paused jobs to sync_jobs queue in original order. Step 7: Emit 'sync:resumed' event. Step 8: Restart worker processing if workers were stopped. Step 9: Log resume action to audit log. Step 10: Return confirmation with estimated completion time.

### cancelSync(syncId)
Cancels and rolls back a sync operation. Parameters: syncId (string UUID). Step 1: Validate sync exists and is in 'processing' or 'paused' status. Step 2: Set atomic cancel flag in Redis. Step 3: Send termination signal to all worker processes for this sync_id. Step 4: Update sync_logs status to 'cancelled' with cancelled_at timestamp. Step 5: Mark all pending sync_jobs as 'cancelled'. Step 6: If rollback_on_cancel is true in config, call rollbackSyncChanges(). Step 7: Clean up any partial changes by querying contact_sync_history for this sync_id. Step 8: Release distributed locks. Step 9: Emit 'sync:cancelled' event. Step 10: Log cancellation with reason and user_id to audit table. Step 11: Send cancellation notification if configured. Step 12: Return summary of completed work before cancellation.

### rollbackSyncChanges(syncId)
Attempts to reverse changes made during a sync. Parameters: syncId (string UUID). Step 1: Query contact_sync_history for all changes with this sync_id. Step 2: Group changes by contact_id. Step 3: For each contact, retrieve before_values from history record. Step 4: Construct rollback payload with original values. Step 5: Execute API call to restore previous state. Step 6: Mark history record with rollback_applied=true and rollback_at timestamp. Step 7: If rollback fails for a contact, log to rollback_failures table. Step 8: Update sync_logs with rollback_attempted=true and rollback_success_count. Step 9: Emit 'rollback:completed' event with results. Step 10: Handle cases where destination record was deleted (cannot rollback).

### fetchContactsForSync(direction, filterCriteria)
Retrieves list of contacts to be synchronized. Parameters: direction (enum), filterCriteria (object with dateRange, source, tags, customQuery). Step 1: Determine source system based on direction (Salesforce for sf_to_renzo). Step 2: Build query based on filterCriteria: add date filters using updated_date or created_date fields. Step 3: Add source filter if specified (e.g., only web-generated leads). Step 4: Add tag filters using JOIN or array containment query. Step 5: If customQuery provided, merge with base query using AND logic. Step 6: Add pagination parameters (limit, offset). Step 7: Execute query against source system API with proper error handling. Step 8: Extract contact IDs from response. Step 9: Deduplicate contact IDs. Step 10: If bidirectional, repeat process for opposite direction and merge results. Step 11: Filter out contacts currently locked by other syncs. Step 12: Return array of contact IDs and total count.

### getSalesforceContact(contactId)
Fetches complete contact record from Salesforce. Parameters: contactId (Salesforce ID string). Step 1: Check rate limiter and wait if necessary. Step 2: Construct SOQL query with all mapped fields from mapping_configurations. Step 3: Include system fields (LastModifiedDate, CreatedDate, SystemModstamp). Step 4: Execute query using Salesforce REST API or Bulk API if part of batch. Step 5: Handle API versioning by checking configured API version. Step 6: Parse response and normalize field names. Step 7: Handle custom objects and nested relationships. Step 8: Cache result in Redis with 5-minute TTL for performance. Step 9: Update rate limiter with API call count. Step 10: Return normalized contact object or throw NotFoundError.

### getRenzoContact(contactId)
Fetches complete contact record from Renzo. Parameters: contactId (Renzo ID string). Step 1: Construct API request to Renzo endpoint /api/contacts/{contactId}. Step 2: Include authorization header with Renzo API token. Step 3: Specify fields to retrieve based on mapping_configurations. Step 4: Execute HTTP GET request with timeout of 10 seconds. Step 5: Parse JSON response. Step 6: Normalize field structure to match internal schema. Step 7: Extract metadata including last_updated timestamp. Step 8: Cache result in Redis with 5-minute TTL. Step 9: Handle Renzo-specific field types (arrays, nested objects). Step 10: Return normalized contact object or throw NotFoundError.

### updateSalesforceContact(contactId, updatePayload)
Updates contact record in Salesforce. Parameters: contactId (string), updatePayload (object with field-value pairs). Step 1: Validate updatePayload against Salesforce schema. Step 2: Check rate limiter and implement backoff if approaching limits. Step 3: Construct PATCH or POST request to Salesforce API. Step 4: Include all required fields for update operation. Step 5: Handle field-level security by checking user permissions. Step 6: Execute update with retry logic for transient failures. Step 7: Parse response to confirm success and retrieve new SystemModstamp. Step 8: If error response, parse error details for specific field failures. Step 9: Update rate limiter counters. Step 10: Invalidate cache for this contact. Step 11: Return success confirmation with updated timestamp or throw ValidationError with field details.

### updateRenzoContact(contactId, updatePayload)
Updates contact record in Renzo. Parameters: contactId (string), updatePayload (object with field-value pairs). Step 1: Validate updatePayload against Renzo schema. Step 2: Construct PUT or PATCH request to Renzo API endpoint. Step 3: Include authorization headers. Step 4: Serialize payload to JSON with proper encoding. Step 5: Execute HTTP request with 15-second timeout. Step 6: Handle 409 Conflict responses indicating concurrent modification. Step 7: If conflict, fetch latest version and retry with merge. Step 8: Parse success response for confirmation. Step 9: Invalidate cache. Step 10: Return updated record with new modification timestamp or throw error.

### loadActiveMappings(direction)
Retrieves active field mappings from database. Parameters: direction (optional filter). Step 1: Query mapping_configurations table with enabled=true. Step 2: If direction specified, filter by direction field. Step 3: Include related transformation rules using JOIN. Step 4: Order by priority field for processing sequence. Step 5: Parse transformation_rules_json into objects. Step 6: Cache mappings in memory with cache invalidation strategy. Step 7: Validate mapping integrity (check source and destination fields exist). Step 8: Build index by source_field for fast lookup. Step 9: Emit 'mappings:loaded' event with count. Step 10: Return array of mapping configuration objects.

### validateSyncConfiguration(config)
Validates sync configuration before execution. Parameters: config (sync configuration object). Step 1: Check required fields are present (direction, batchSize). Step 2: Validate batchSize is between 1 and 2000. Step 3: Validate direction is one of allowed values. Step 4: Check filterCriteria if present has valid date format. Step 5: Validate conflict resolution strategy is supported. Step 6: Check API credentials are configured for required systems. Step 7: Test API connectivity with lightweight ping. Step 8: Validate mappings exist for specified direction. Step 9: Check sync is not redundant with recently completed identical sync. Step 10: Return validation result object with isValid boolean and errors array.

### calculateSyncProgress(syncId)
Computes current progress of sync operation. Parameters: syncId (string). Step 1: Query sync_logs for estimated_contacts count. Step 2: Query sync_jobs for sum of contacts_processed from completed batches. Step 3: Calculate percentage: (processed / estimated) * 100. Step 4: Query sync_jobs for count of pending, processing, completed batches. Step 5: Calculate average processing rate: total_processed / elapsed_time. Step 6: Estimate remaining time: remaining_contacts / avg_rate. Step 7: Get current batch details if one is processing. Step 8: Build progress object with percentage, counts, timing estimates. Step 9: Include error rate statistics. Step 10: Return progress object for dashboard display.

### getRecentSyncs(limit, offset, filters)
Retrieves sync history for dashboard display. Parameters: limit (integer), offset (integer), filters (object with status, direction, dateRange). Step 1: Build base query on sync_logs table. Step 2: Apply status filter if provided using WHERE clause. Step 3: Apply direction filter if provided. Step 4: Apply date range filter on started_at field. Step 5: Order by started_at DESC for most recent first. Step 6: Apply limit and offset for pagination. Step 7: Execute query with proper indexing. Step 8: For each result, calculate duration and success rate. Step 9: Enrich with related error count from sync_logs_errors. Step 10: Return array of sync summary objects with total count for pagination.
